# 美心 AI 行政助手系统设计文档

状态：第一版架构基线
更新日期：2026-09-18

## 1. 设计目标

系统面向约 50 名学生、4 名行政人员和若干教师，以低学习成本完成“建档—排课—签到—课消—续费—教师课时—工资基础核算—经营日报”的闭环。首期采用模块化单体架构，优先保证数据正确、可追溯和可恢复。

## 2. 用户角色

| 角色 | 主要任务 | 权限边界 |
|---|---|---|
| 行政人员 | 学生/家长维护、课程维护、排课、签到复核、缴费登记、Excel 导入、日常查询 | 可操作日常业务；不可修改系统级权限和已确认工资 |
| 教师 | 查看个人课表、记录/确认学生出勤、查看个人课时 | 仅访问本人课程及必要的学生联系信息；不可查看缴费、其他教师数据 |
| 负责人 | 全局查询、异常处理、报表、工资审核、配置和用户管理 | 全部业务权限；关键操作仍保留审计记录 |

建议后续增加只读“审计/财务”权限时，沿用角色权限表扩展，不在代码中散落角色名称判断。

## 3. 技术方案比较与结论

### 方案 A：FastAPI + Jinja2/HTMX + PostgreSQL（推荐）

- 优点：一个 Python 单体即可提供页面与 API；数据导入、AI 调用生态成熟；未来可给小程序或“校精灵”适配器复用 API；HTMX 避免独立 SPA 的构建和状态管理成本。
- 缺点：登录、后台页面和权限需要按业务实现；团队需遵守清晰分层以避免路由变厚。
- 适用：当前规模和未来适度集成需求，部署维护成本低。

### 方案 B：Django + Django Templates/HTMX + PostgreSQL

- 优点：认证、ORM、迁移和管理后台内置，常规 CRUD 开发快，生态成熟。
- 缺点：若直接把 Django Admin 当最终产品，界面对非技术行政人员不够友好；对外 API 需增加 DRF 或额外层，框架概念更多。
- 适用：以后台 CRUD 为绝对主导、团队熟悉 Django 的情况，是可靠备选。

### 方案 C：FastAPI + React/Vue SPA + PostgreSQL

- 优点：复杂交互和前后端分工能力强，适合大型产品。
- 缺点：两套工程、认证、构建与部署链路，测试和维护成本明显增加；对 4 名行政人员的内部系统收益不足。
- 适用：未来出现大量实时交互、独立前端团队或多端共用时再评估。

结论：选择方案 A。正式环境使用托管 PostgreSQL 或单机 PostgreSQL；SQLite 仅用于本地开发、自动化测试和单人试用。前端不建立独立 Node SPA。AI 通过可替换的服务接口调用大模型，未配置 API 时核心业务仍可正常运行。

## 4. 总体架构

```text
浏览器（行政/教师/负责人）
        │ HTTPS
        ▼
FastAPI 单体应用
  ├─ 页面路由 + Jinja2/HTMX
  ├─ REST API（未来小程序/集成复用）
  ├─ 业务服务（排课、签到、课消、缴费、工资）
  ├─ 导入服务（Excel 校验、预览、提交）
  └─ AI 分析服务（仅读取已确认结构化数据）
        │
        ├─ PostgreSQL（业务事实、审计、提醒）
        ├─ 文件存储（导入原件/错误报告，受控访问）
        └─ 大模型 API（可选、超时不影响主流程）
```

采用模块化单体：各业务模块边界清晰，但共享一次部署、一个数据库和统一权限。低频任务初期用系统计划任务或受控命令运行；只有实际出现可靠性需求时才引入专用任务队列。

## 5. 核心业务流程

### 5.1 学生建档与购买课时

Excel 导入或手工建档 → 关联家长 → 建立选课/课时账户 → 登记缴费 → 经确认后生成课时入账流水 → 显示可用余额。

### 5.2 排课、签到与自动课消

建立课程 → 创建排课并指定教师/教室/学生 → 教师或行政签到 → 行政确认 → 针对“到课/按规则请假”等状态生成唯一课消流水 → 更新课时账户汇总。撤销确认时不删除流水，而创建冲正并留下原因。

### 5.3 教师课时与工资基础核算

已完成且已确认的排课 → 按教师计薪规则生成教师课时记录 → 负责人按结算周期复核 → 生成工资计算单 → 锁定。系统输出的是工资基础计算，不替代最终财务发放和法定薪资处理。

### 5.4 AI 日报

定时汇总当日已确认数据 → 规则引擎先计算出勤、课消、余额、异常 → 可选调用大模型组织为易读日报 → 保存生成依据和版本 → 负责人查看。大模型不得修改业务记录，也不得臆造缺失数据。

## 6. 模块设计

### 6.1 学生管理

- 输入：学生编号、姓名、出生日期/年龄、状态、就读信息、家长联系方式、备注；Excel 学生名单。
- 处理：字段校验、重复识别、家长关联、状态变更、敏感字段权限控制；年龄由出生日期动态计算。
- 输出：学生档案、家长关系、选课与余额摘要、历史操作记录、导入错误报告。

### 6.2 课程管理

- 输入：课程编号、名称、类别、默认课时单位、适用年级、标准价格、状态。
- 处理：版本化关键计费参数；停用课程不影响历史记录；建立学生选课和课时账户。
- 输出：课程列表、课程详情、在读学生、课时账户汇总。

### 6.3 排课

- 输入：课程、教师、开始/结束时间、教室、学生名单、重复规则。
- 处理：教师/学生/教室冲突检查，生成单次课次；批量调整时保留变更记录。
- 输出：日/周课表、冲突提示、教师个人课表、待签到课次。

### 6.4 签到

- 输入：课次、学生、出勤状态（到课/迟到/请假/缺勤/补课）、记录人、备注。
- 处理：检查学生是否属于课次；防重复提交；区分教师提交与行政确认；记录修改轨迹。
- 输出：签到清单、待确认项、出勤统计、异常名单。

### 6.5 课消

- 输入：已确认签到、课程扣减规则、每次扣减课时；人工调整需原因和审批人。
- 处理：事务内校验余额并生成不可变课时流水；使用签到唯一键保证幂等；撤销采用冲正；余额不足进入异常队列而非静默负数。
- 输出：课消记录、账户余额、冲正记录、余额不足异常。

### 6.6 缴费

- 输入：学生、课程/套餐、金额、购买课时、付款日期、方式、收据号、经办人、凭证备注。
- 处理：草稿—已确认—已作废状态流；确认后生成金额记录和课时入账，重复收据号校验；作废使用冲正。
- 输出：缴费台账、课时入账、欠费/续费候选、期间收入汇总。

### 6.7 教师管理

- 输入：教师编号、姓名、联系方式、状态、可授课程、基础计薪规则、生效日期。
- 处理：权限隔离、规则版本化、离职停用；不覆盖历史计薪标准。
- 输出：教师档案、可授课程、个人课表、课时与工资基础汇总。

### 6.8 工资统计

- 输入：结算周期、已确认教师课时记录、适用计薪规则、补贴/扣项及说明。
- 处理：规则计算、异常检测、人工复核、锁定与重新打开审计；金额使用定点精度。
- 输出：教师工资基础计算单、明细、差异与异常提示、Excel 导出。

### 6.9 AI 分析

- 输入：已确认的课程、出勤、课消、余额、缴费和教师课时聚合数据。
- 处理：确定性规则先发现低余额、异常缺勤、漏签到、教师课时波动；大模型只做摘要、归因候选和表达；记录提示词版本、数据时间窗和响应状态。
- 输出：经营日报、续费提醒、异常提醒、需人工确认的建议。所有建议必须链接到原始数据。

## 7. Excel 数据导入

首批支持学生、课程、教师三类 `.xlsx` 文件，流程固定为：上传 → 病毒/大小/类型检查 → 表头映射 → 逐行校验 → 预览新增/更新/跳过/失败 → 用户确认 → 单事务或分批写入 → 生成结果报告。

设计要求：

- 提供中文模板和示例，不要求行政人员调整为数据库字段名。
- 以学生编号、课程编号、教师编号作为幂等业务键；姓名不能单独作为唯一键。
- 预览阶段不写业务表；提交阶段记录导入批次和每行结果。
- 允许部分失败，但必须明确展示失败行和原因；重新导入同一文件不会重复新增。
- 原文件受控保存并设保留期限；生产数据导入前先备份。

## 8. 权限、安全与审计

- 账号由负责人创建，初始密码强制修改；会话使用安全 Cookie，生产强制 HTTPS。
- 所有服务端接口做角色和数据范围校验，不能只隐藏前端按钮。
- 登录、导入、缴费确认、签到确认、课消冲正、工资锁定等写入审计日志。
- 个人信息最小化展示；导出文件设置有效期；日志脱敏。
- 数据库每日备份，备份加密并与应用主机分离；定期恢复演练。

## 9. 可用性与运维

- 首页展示“今日课程、待确认签到、低课时学生、异常事项”四类行动入口。
- 表单给出中文示例与就地错误，不使用数据库术语；危险操作需要明确结果说明。
- 目标：常规页面在机构网络下 2 秒内可交互；AI 超时或失败不影响业务页面。
- 提供 `/health/live` 和 `/health/ready` 健康检查；错误日志带请求 ID，不记录敏感值。

## 10. 当前边界与待确认事项

进入业务开发前需与负责人确认：现有 Excel 样例及字段、课程/课时单位、请假和缺勤是否扣课、余额能否为负、多人/一对一计费差异、教师计薪规则、结算周期、缴费退款流程、教室资源、“校精灵”是否有可用导出或 API、AI 服务供应商与数据合规要求。
